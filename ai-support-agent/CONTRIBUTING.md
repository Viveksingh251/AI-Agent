# Contributing to the AI Customer Support Agent

Thanks for contributing! This guide covers the workflow, standards, and checks your change must pass.

---

## 1. Getting Started

```bash
git clone <repo-url> && cd ai-support-agent
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env             # fill in OPENAI_API_KEY, DATABASE_URL, SECRET_KEY
```

See the [README](README.md) for database setup, seeding, and document ingestion.

## 2. Development Workflow

1. **Create a branch** from `main`:
   ```bash
   git checkout -b feat/warranty-tool
   ```
   Prefixes: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`, `chore/`.
2. **Make your change** — keep PRs focused; one logical change per PR.
3. **Add/adjust tests** — every bug fix or feature needs coverage (see §4).
4. **Run the checks locally** (§5) — all of them, before pushing.
5. **Open a PR** with a short description, screenshots for UI changes, and a note on any config/migration impact.

### Commit messages

Use Conventional Commits:

```text
feat(tools): add get_warranty_status tool with ownership checks
fix(rag): guard against empty FAISS index on cold start
docs: document /metrics endpoint in API.md
```

## 3. Project Layout — where to make changes

| Change | Location | Guide |
|---|---|---|
| New agent tool | `agent/tools/`, `agent/tools/registry.py` | [docs/ADDING_TOOLS.md](docs/ADDING_TOOLS.md) |
| New graph node / routing | `agent/nodes.py`, `agent/graph.py`, `agent/state.py` | [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) |
| New HTTP endpoint | `api/routers/`, `api/schemas.py` | [docs/API.md](docs/API.md) |
| New config variable | `app/config.py` **and** `.env.example` (always both) | — |
| DB schema change | `database/models.py` + Alembic revision | `make revision m="..."` |
| Prompt tuning | `agent/prompts/` | — |

## 4. Testing Standards

- Framework: **pytest** with `pytest-asyncio` (`asyncio_mode = auto` — async tests need no decorator).
- Tests live in `tests/`; name files `test_<area>.py`.
- Markers: `integration` (end-to-end graph/API), `authz` (authorization/tenancy).
- **Required coverage for a new tool**: owner allowed, other customer denied, staff allowed, failure path — see [docs/ADDING_TOOLS.md §4](docs/ADDING_TOOLS.md#step-4--test-it).
- No test may require real network/LLM/DB access; mock external services (see existing fixtures in `tests/conftest.py`).

## 5. Checks Before Every PR

```bash
make check        # runs all of the following
```

Equivalent manual commands:

```bash
black .                                  # formatting (line length per pyproject.toml)
ruff check .                             # linting
mypy app agent api database rag          # static typing
pytest -v                                # full suite (181+ tests)
```

All four must pass. CI runs the same suite.

## 6. Code Standards

- **Python 3.11+**, full type hints on public functions; `from __future__ import annotations` in new modules.
- **Async everywhere** in API/agent/database code — never block the event loop.
- **Structured results over exceptions** in agent tools (`{"success": False, "error": ...}`); exceptions are reserved for truly unexpected failures.
- **Security first**: never trust LLM-supplied identity — authorization context is injected server-side (see ARCHITECTURE.md §3). Never log secrets or full customer PII; use ids.
- **Fail-safe observability**: monitoring code must never break the request path; guard optional imports.
- Keep modules under a few hundred lines; prefer adding a new module over growing a god-file.
- Update docs (README / docs/) whenever behavior or config changes.

## 7. Database Migrations

```bash
make revision m="add warranty table"   # autogenerate revision
make migrate                           # alembic upgrade head
```

Review autogenerated migrations before committing — autogenerate misses server defaults and data migrations. Never edit an applied migration; add a new one.

## 8. Reporting Bugs & Security Issues

- **Bugs**: open an issue with repro steps, expected vs actual behavior, and the `request_id` from the error response (this correlates logs and traces).
- **Security vulnerabilities**: do **not** open a public issue. Email the maintainers privately (see CODEOWNERS / repo settings) and allow time for a fix before disclosure.

## 9. PR Review Checklist

Maintainers check for:

- [ ] Tests pass and cover the change
- [ ] `make check` clean (black, ruff, mypy)
- [ ] Authorization considered (new endpoints/tools enforce RBAC/ownership)
- [ ] No secrets in code, logs, or fixtures
- [ ] Config variables documented in `.env.example`
- [ ] Docs updated (README / ARCHITECTURE / API / ADDING_TOOLS as applicable)
- [ ] Migration reviewed if schema changed
